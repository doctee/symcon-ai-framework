# 212 Native MQTT Private Pilot Operating Policy

**Case study:** Navimow native IP-Symcon module
**Status:** Operating policy complete; observation harness and activation
remain closed
**Date:** 2026-07-29
**Scope:** Define one bounded 72-hour receive-only private-pilot operation
after the deadline-hardening closure

## 1. Purpose

Step 211 accepted the native MQTT deadline hardening within the existing
disabled-by-default private-pilot boundary.

The technical foundation is now proven:

- native WebSocket/MQTT connection and natural ingress;
- Receiver-to-Account forwarding;
- targeted REST reconciliation;
- bounded reconnect handling;
- OAuth credential rotation;
- retained-Core adoption after a Symcon restart;
- complete credential cleanup;
- unchanged variables and Archive Control contracts.

The next gap is operational rather than architectural. This step defines how
the receive-only transport may be used for one longer but bounded private
pilot without treating MQTT as public state authority or enabling unattended
production operation.

It performs no publication, productive code change, Symcon access, MQTT
activation, restart, mower command or credential retrieval.

## 3. Operating Classification

This policy authorizes planning for:

```text
bounded, monitored, receive-only private pilot
```

It does not authorize:

- always-on or open-ended MQTT operation;
- public or store-ready MQTT support;
- MQTT as direct authority for Device variables;
- MQTT publishing;
- mower commands through MQTT;
- automatic extension beyond the pilot deadline;
- an induced network outage or service restart;
- a release tag.

REST remains the sole authority for public mower state and commands.

## 4. Pilot Window

Selected nominal window:

```text
maximum duration: 72 hours
earliest normal completion: 48 hours
target mowing cycles: 3
minimum successful mowing cycles: 2
```

Normal early completion after 48 hours is permitted only when all mandatory
evidence is already present:

1. at least two complete scheduled mowing cycles;
2. at least one successful OAuth/MQTT credential rotation;
3. continued REST authority and reconciliation;
4. no unresolved transport anomaly;
5. all compatibility contracts unchanged.

The pilot stops at 72 hours regardless of mowing schedule or evidence count.
If fewer than two complete scheduled cycles occurred naturally, the result is
`INCONCLUSIVE`, not a reason to start the mower manually solely for the test.

No pilot window may be silently extended.

## 5. Safety and Authority Boundary

Throughout the window:

- MQTT remains receive-only;
- MQTT messages only trigger bounded targeted REST reconciliation;
- public variables are updated from REST responses;
- no MQTT payload directly writes `VehicleState`, `Online`, `BatteryLevel` or
  `LastStatusUpdate`;
- all mower commands remain REST-only and user initiated;
- no command is generated by the observation harness;
- normal scheduled mowing is not changed for the pilot;
- the official app and physical safety controls remain available;
- MQTT failure does not suspend normal REST polling;
- no Core instance is created, deleted, replaced or reparented;
- `MC_ReloadModule()` remains prohibited.

Because the pilot does not command the mower, uninterrupted visual supervision
for all 72 hours is not required. Normal manufacturer safety requirements for
scheduled mowing still apply.

## 6. Pilot Objectives

The pilot must answer:

1. Does native MQTT remain healthy over multiple days?
2. Does natural MQTT ingress accompany at least two complete mowing cycles?
3. Does each accepted MQTT hint produce bounded REST reconciliation?
4. Does normal OAuth refresh rotate MQTT credentials without manual action?
5. Do short natural connectivity gaps recover within the existing limits?
6. Does REST continue independently when MQTT data is absent?
7. Do variables, logging and command evidence remain unchanged?
8. Can the transport be disabled and cleaned completely after prolonged use?

This pilot does not evaluate MQTT command semantics or direct MQTT state
mapping.

## 10. Observation Schedule

The productive module performs its own Core-health observation every
60 seconds. The external pilot harness records bounded read-only snapshots:

| Point | Required capture |
|---|---|
| before activation | two equal inactive baselines |
| after activation | two equal active baselines |
| `+15 min` | early stability |
| `+60 min` | first-hour health |
| every 6 hours | regular bounded checkpoint |
| each detected credential rotation | pre/post counter and health projection |
| each mowing-cycle start | state, Receiver and reconciliation baseline |
| each mowing-cycle completion | bounded counter deltas and REST result |
| any detected anomaly | temporary 60-second diagnostic cadence |
| normal end | final active projection before cleanup |
| after cleanup | immediate and delayed closure |

The six-hour schedule yields no more than 13 regular duration checkpoints.
Cycle, rotation and anomaly records are separately bounded.

The harness must not poll private credentials, payloads or topics.

## 12. OAuth and Credential Rotation

At least one natural OAuth refresh and matching MQTT credential rotation must
be observed.

Expected sequence:

1. OAuth expiry moves forward without manual action;
2. `credentialRotations` increases by one;
3. the owned transport is cleaned;
4. one rotation connection is scheduled after five seconds;
5. connection attempts and successes each increase by one;
6. connection failures do not increase;
7. Core returns to `ShadowActive/healthy`;
8. REST remains connected and operational.

Do not press `Token aktualisieren`, initiate OAuth or call a manual refresh
during the pilot.

If passive OAuth refresh fails, the module must clean and suspend MQTT.
`ReauthRequired=true` or loss of REST authentication is a hard stop.

## 13. Mowing-Cycle Evidence

A complete natural cycle is:

```text
Docked -> Running -> Docking -> Docked
```

Equivalent additional symbolic intermediate states may occur. The pilot
requires evidence that:

- scheduled mowing started without a pilot command;
- Receiver counters advanced during the active period;
- MQTT hints were accepted or their absence was explicitly recorded;
- targeted REST reconciliation remained bounded;
- the public `VehicleState` came from REST;
- final `Docked` was recorded normally;
- archive logging remained enabled;
- no command-evidence variable changed because of the pilot.

Missing MQTT messages during poor mower connectivity do not alone fail a
cycle. REST must continue to capture the authoritative transition.

## 14. Connectivity and Reconnect Policy

Poor mower connectivity normally appears as absent or delayed messages while
the Symcon broker connection remains healthy. In that case:

- do not reconnect the broker solely because no mower message arrived;
- continue normal REST polling;
- record the gap only when it overlaps a known mowing cycle;
- wait for natural ingress recovery.

When the owned MQTT/WebSocket transport itself becomes unhealthy, the existing
episode contract applies:

```text
attempt 1: after 60 seconds
attempt 2: after 300 seconds
attempt 3: after 900 seconds
attempt 4: prohibited
```

Authentication, ownership and configuration errors are not retryable.

A single recovered transport episode may remain within the pilot when:

- recovery completes within the three-attempt bound;
- REST remains healthy;
- credentials and ownership remain valid;
- no reconnect exhaustion occurs;
- the event is fully captured.

A second unexpected transport episode or any exhausted episode stops the first
72-hour pilot. This conservative limit may be reviewed from actual evidence.

## 15. Restart Policy

No planned Symcon restart belongs to this pilot. Restart recovery was already
proved separately.

If an unplanned service restart occurs:

- do not initiate another restart;
- allow up to five minutes for service availability;
- require retained-Core observation within the `+180 s` Axis-B deadline;
- require healthy adoption without an Account reconnect;
- capture the persisted observation timeline;
- continue only when the complete step-210 contract is reproduced.

Any restart recovery failure ends the pilot and triggers cleanup as soon as
control returns.

## 16. Stop Conditions

Stop the pilot immediately when any hard condition is observed:

- `ReauthRequired=true`;
- REST authentication or normal REST polling fails persistently;
- lifecycle enters `ConfigurationError`;
- ownership, pairing, topology or subscriptions drift;
- credential cleanup reports an error;
- reconnect exhaustion occurs;
- a second unexpected transport-disconnect episode occurs;
- MQTT publishing or a mower command is attempted;
- Device variable identity or Archive logging changes;
- command-evidence variables change without a user command;
- public state is written directly from MQTT;
- diagnostic output exposes private material;
- the observation harness loses reliable evidence continuity for more than
  six hours;
- the 72-hour deadline is reached.

At a hard stop, do not retry activation under the same authorization.

## 17. Normal Completion Criteria

The pilot passes when:

- elapsed duration is at least 48 hours and at most 72 hours;
- at least two complete natural mowing cycles are recorded;
- at least one credential rotation succeeds;
- MQTT remains receive-only;
- REST remains authoritative and continuously usable;
- no reconnect exhaustion occurs;
- at most one fully recovered unexpected transport episode occurs;
- all accepted MQTT hints result in bounded REST reconciliation;
- no unexplained sustained REST/MQTT mismatch remains;
- variables, actions, command evidence and Archive logging remain unchanged;
- mandatory cleanup passes immediately and after at least 180 seconds.

Classification:

| Outcome | Meaning |
|---|---|
| `PASS` | every completion criterion satisfied |
| `INCONCLUSIVE` | safe closure, but fewer than two natural cycles or no observable rotation |
| `FAIL` | a technical, authority, privacy or cleanup contract failed |
| `ABORTED` | operator stopped safely before sufficient evidence |

`INCONCLUSIVE` does not authorize an automatic extension or a second pilot.

## 20. Observation Harness Requirements

Before activation, implement and test a bounded private harness that:

- stores output only below `private/`;
- records no secret values or private identifiers in public artifacts;
- uses read-only Symcon projections during the pilot;
- has a fixed 72-hour deadline;
- limits regular snapshots to the defined schedule;
- temporarily increases cadence only for a bounded anomaly;
- detects credential-rotation and transport-counter changes;
- identifies symbolic mowing-cycle boundaries from authoritative REST state;
- validates variable/archive hashes without changing them;
- never calls a mower action, MQTT Connect or service restart;
- does not mutate Symcon except through the separately authorized activation
  and mandatory cleanup procedures;
- resumes safely after a local harness interruption without duplicating
  activation;
- generates a deterministic machine-readable closure summary.

The harness must pass offline tests with a synthetic clock before any live
activation.

## 22. Architecture Decisions

### AD-NAV-752: Select a 72-hour maximum pilot

**Decision:** Use three calendar days as the hard upper bound.

**Reason:** This provides a realistic chance to observe two or three scheduled
mowing cycles and multiple normal token lifecycles without creating an
open-ended credential-bearing operation.

### AD-NAV-753: Permit completion after 48 hours only with full evidence

**Decision:** Require at least two complete cycles and one credential rotation
before an early normal stop.

**Reason:** Elapsed time alone does not prove the intended operating paths.

### AD-NAV-754: Keep scheduled mowing unchanged

**Decision:** Do not manually start the mower solely to satisfy the pilot.

**Reason:** Receive-only operation should be observed under normal use and
must not create an additional physical test action.

### AD-NAV-755: Use checkpoint monitoring over continuous external polling

**Decision:** Rely on the module's 60-second lifecycle and collect bounded
external checkpoints plus event-driven anomaly evidence.

**Reason:** This provides operational visibility without producing an
unbounded private log or unnecessary Symcon load.

### AD-NAV-756: Allow at most one naturally recovered transport episode

**Decision:** Continue after one fully bounded recovery, but stop on a second
episode or exhaustion.

**Reason:** One natural recovery is useful pilot evidence; repeated failures
indicate that the first long-running pilot should end for analysis.

### AD-NAV-757: Require a tested private harness before activation

**Decision:** Do not operate the 72-hour pilot through ad hoc manual probes.

**Reason:** Multi-day evidence, deadline enforcement and mandatory cleanup
need deterministic, resumable and privacy-safe tooling.

### AD-NAV-758: Keep the pilot disabled by default after closure

**Decision:** Every result returns to credential-free `Disabled`.

**Reason:** A bounded private-pilot pass does not itself authorize permanent
operation.
